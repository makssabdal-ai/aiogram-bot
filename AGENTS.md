# Инструкции для работы с проектом

## Назначение и стек

Боты кондитерской для Telegram и VK: каталог тортов, работы, отзывы и оформление заказов.
Оба бота используют одну PostgreSQL-базу; уведомления о заказах поступают в Telegram.
Стек: Python, asyncio, aiogram 3, aiogram_calendar, aiohttp, asyncpg, python-dotenv.
Версии зависимостей закреплены в [requirements.txt](requirements.txt).
SQLAlchemy и aiosqlite перечислены в зависимостях, но слой данных реализован на asyncpg.
Версия Python отдельно не закреплена; в коде используется синтаксис типов `str | None`.

## Карта проекта

- `main.py` — запуск Telegram polling, создание БД и диспетчера.
- `main_vk.py` — запуск VK Long Poll и проверка необходимых переменных окружения.
- `database/db.py` — пул PostgreSQL, создание/расширение схемы и SQL-запросы.
- `database/migrations/` — повторяемые SQL-миграции, вызываемые из `init_tables()`.
- `handlers/common.py` — старт, помощь, главное меню и контакты Telegram.
- `handlers/catalog.py` — каталог, карточки, работы и отзывы Telegram.
- `handlers/order.py` — согласие, шаги заказа, подтверждение и уведомления Telegram.
- `handlers/__init__.py` — регистрация Telegram-роутеров.
- `forms/user.py` — состояния Telegram FSM в классе `Form`.
- `utils/` — общие справочники, валидаторы, согласие и Telegram-клавиатуры.
- `vk_bot/bot.py` — сценарии VK, состояния пользователей и уведомления в Telegram.
- `vk_bot/client.py` — HTTP-клиент VK API и Long Poll; `vk_bot/keyboards.py` — клавиатуры VK.
- `files/catalog/`, `files/reviews/`, `files/works/` — отслеживаемые Git фото и видео.
- `docs/personal_data_consent.md` — текст согласия на обработку персональных данных.
- `tests/test_bot.py` — модульные тесты слоя БД на unittest и моках asyncpg.
- `tests/test_platform_ids.py` — проверка ID, миграции и импорта в изолированных схемах PostgreSQL.
- `tests/test_vk_gallery.py` — страницы работ, отзывы и проверка доставки VK-вложений на моках API.
- `scripts/import_vk_media.py`, `data/vk_media.json` — импорт VK-медиа и его входные данные.

## Команды

Выполнять из корня проекта. `python` ниже — интерпретатор выбранного окружения.
Для существующего окружения Windows можно использовать `.\.venv\Scripts\python.exe`.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe main.py
.\.venv\Scripts\python.exe main_vk.py
.\.venv\Scripts\python.exe -m unittest discover -s tests -p "test_*.py"
```

Две команды запуска — отдельные процессы для соответствующих платформ.
Запуск подключается к БД, выполняет DDL через `init_tables()` и начинает получать события.
Он не является проверкой без внешних последствий.
Скриптов сборки, настроенных команд линтинга/форматирования и CI в репозитории нет.
Установка и отдельный запуск платформ описаны в [readme.md](readme.md); шаблон настроек — `.env.example`.

## Конфигурация

- Telegram читает `BOT_TOKEN` и `DATABASE_URL`; `ADMIN_IDS` нужен для уведомлений о заказах.
- VK требует `VK_GROUP_TOKEN`, `VK_GROUP_ID`, `DATABASE_URL`, `BOT_TOKEN`, `ADMIN_IDS`.
- `ADMIN_IDS` разбирается как список идентификаторов через запятую.
- `main.py` загружает `.env` обычным `load_dotenv()`, `main_vk.py` — с `override=True`.
- `PERSONAL_DATA_CONSENT_URL` необязателен; ссылка по умолчанию задана в `utils/consent.py`.
- `BOT_PROXY` — необязательный HTTP-прокси для обоих ботов и уведомлений VK в Telegram.
- `BOT_CA_FILE` — необязательный PEM-файл дополнительной цепочки сертификатов для HTTP-сессий VK.
  Проверка сертификатов остаётся включённой; сессии создаются в `utils/http.py`.
- `.local/` исключён из Git и может хранить локальные сертификаты.
- `.env`, `.venv/`, `.python-nuget/`, `__pycache__/` и `*.pyc` исключены через `.gitignore`.

## Подтверждённые архитектурные соглашения

- Обработчики и работа с сетью/БД асинхронные; SQL находится в `Database`.
- SQL-параметры передаются отдельно от запроса через `$1`, `$2` и далее.
- Telegram получает `Database` через `dp["db"]` и аргумент `db` обработчиков.
- Порядок роутеров: common → catalog → order; в order есть общий обработчик сообщений.
- Telegram хранит шаги заказа в FSM; VK — в словарях экземпляра `VKCakeBot`.
  Постоянное хранилище незавершённых диалогов не настроено.
- Общие варианты тортов, размеров и доставки находятся в `utils/constants.py`.
  Клавиатуры и обработчики обеих платформ используют соответствующие ключи команд.
- Интерфейс русскоязычный; Telegram использует HTML, VK преобразует текст для своей платформы.
- Пользователи платформ разделены: `users.telegram_id` и `users.vk_id`, оба положительные.
  В orders/reviews `user_id` остаётся Telegram ID, `vk_id` содержит VK ID.
  Методы Database принимают ровно один из `telegram_id`/`vk_id`; отрицательные ID недопустимы.

## Данные и особенности

- Схема создаётся в `Database.init_tables()`: users, catalog, works, reviews, orders.
  Изменения существующих таблиц оформлены там же через `ADD COLUMN IF NOT EXISTS`.
  `database/migrations/001_vk_identity.sql` переносит прежние отрицательные ID и VK-медиа заказов.
  Инициализация выполняется в транзакции с advisory lock; отдельного migration framework нет.
- Подключение asyncpg требует SSL для удалённых адресов; для `localhost`, `127.0.0.1`, `::1` SSL отключён.
- Медиа представлены идентификаторами платформ: `file_id` и `vk_file_id`,
  с отдельными `media_type` и `vk_media_type`. Не считайте эти ID взаимозаменяемыми.
- VK может отбросить вложения без ошибки отправки текста: `VKClient` сверяет их через `messages.getById`.
  Смещение страницы работ изменяется только после успешной проверки; актуальность `access_key` важна.
- Файлы в `files/` не наполняют таблицы автоматически и не являются резервной копией БД.
- `python -m scripts.import_vk_media` проверяет сопоставления; `--apply` записывает VK-медиа.
  Каталог сопоставляется по названию; отзывы/работы добавляются отдельными VK-строками без дублей.
  Порядок подготовки базы и резервного копирования см. в [readme.md](readme.md).
- `date_delivery` хранится текстом в формате `%d.%m.%Y`; валидатор требует минимум 3 дня.
  Обработчики ограничивают число заказов на дату тремя; это проверка приложения.
- Текст согласия: [docs/personal_data_consent.md](docs/personal_data_consent.md).
  Версия документа и формирование ссылки — в `utils/consent.py`; факт согласия хранится в users.

## Выбор проверок — рекомендации

- Для SQL и отображения полей заказа запускайте unittest-команду выше.
  Имеющиеся тесты проверяют добавление пользователя/заказа, каталог и подсчёт заказов.
  Тесты `test_bot.py` используют моки и не проверяют реальную схему или подключение.
- С `TEST_DATABASE_URL` та же unittest-команда включает интеграционные тесты в отдельных схемах.
  Проверяются разделение платформ, миграция старых данных и повторный импорт; схемы удаляются после теста.
- Для изменений синтаксиса можно выполнить `python -m compileall -q main.py main_vk.py database handlers forms utils vk_bot scripts tests`.
  Команда создаёт игнорируемые `__pycache__`, но не запускает ботов.
- Для клавиатур, FSM и валидации проверяйте связанные обработчики обеих платформ;
  существующие тесты не покрывают эти сценарии. При добавлении тестов используйте текущий unittest.
- Для изменений схемы дополнительно нужна проверка на отдельной тестовой PostgreSQL-базе;
  прохождение мок-тестов не подтверждает корректность DDL.
- Для документации сверяйте пути, команды и имена настроек с исходниками;
  запуск ботов для такой проверки не нужен.
